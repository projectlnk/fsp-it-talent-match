# Рабочие кабинеты и демонстрация механик

Дата: 10.10.2026. Все изменения выполнены локально. SSH, сервер, deployment,
commit и push не использовались. README не изменялся. Обнаруженные в README
маркеры конфликта существовали до этой работы; содержание отсутствующего ТЗ
или «итогов созвона» не придумывалось.

## Сверка и принятый объём

Готовый backend: регистрация и подтверждение email, JWT/cookie и роли,
профили/навыки/опыт, задания и попытки со снимками вопросов, категории и
кулдаун, поиск/фильтры/пагинация/объяснения, адресные Offer и ответы,
публикация, интеграционный слой ФСП, PDF владельца.

До работы потребности, вакансии, отклики, рейтинг, встречи, сообщения и
перемотка времени в рабочих кабинетах отсутствовали. /design-preview был
макетом с данными и состоянием браузера. Добавлен совместимый модуль career,
не вторая реализация поиска, приглашений, PDF или интеграции ФСП.

Веб-страницы используют FastAPI/Jinja2 и транзакционные сервисы, существующий
CSS/JS; новый frontend-фреймворк, сборщик или очередь не добавлялись.

- Кандидат: профиль, редактирование, навыки, опыт, тесты и история,
  категория, входящие приглашения, привязка/импорт/отвязка ФСП,

  на потребность/поиск/приглашения из макета заменены реальными.

## Подбор и активность: решение команды

Потребность хранит роль, задачи/условия, специализацию, грейд, навыки,
зарплату в рублях, формат и способ связи. Канонические грейды прежние:
intern, junior, middle, senior. Проверяются backend-схемой.

Рекомендации сначала ограничиваются опубликованной подтверждённой
категорией (специализация + грейд) и форматом. Далее используется прежняя
формула rank_candidate: тест до 70, достижения ФСП до 20, релевантность
дисциплины до 10. Добавлен объяснимый компонент заявленных навыков запроса
до 20: 20 * matched / requested. Это баллы соответствия, не процент
правильных ответов. Навыки прямо подписаны как заявленные. Кандидат без ФСП
не исключается. Равенство разрешается ID профиля; пагинация после сортировки.

Самостоятельные отклики допускаются и при скрытом профиле или отсутствии
подходящей категории. Для них используется тот же расчёт компонентов,
соответствие подтверждённой категории отмечается отдельно и сортируется
первым. Их данные доступны только владельцу вакансии. Скрытый профиль от
этого не появляется в рекомендациях или общем поиске.

Активность (настраиваемые сроки; выбранная простая формула баллов):

- заполненное название/описание/отрасль/контакт компании: 5, один раз;
- первое решение по каждому кандидату: 2, максимум 20 для этого компонента;
- двустороннее внутреннее общение: 3, один раз на компанию/кандидата;
- подтверждённое собеседование: 10, один раз на компанию/кандидата;
- двусторонне подтверждённый найм: 30, один раз на компанию/кандидата;
- обработанная доля: 10 * handled / total, только при ≥3 разных кандидатах.

Сумма событий + компонент доли; равенство по ID компании. Просмотры,
создание вакансий, массовая отправка приглашений и публичные отзывы баллов
не дают. Повторные основания защищены уникальным ограничением и блокировкой
компании. Формула ограничивает очевидное повторное начисление, но не
доказывает фактический найм и не устраняет сговор разных тестовых аккаунтов.

## Приватность и согласия

Новый кандидат остаётся скрытым. В регистрации добавлен явный checkbox
обработки данных. API совместим: поле processing_consent добавлено с false
по умолчанию; отсутствие согласия не мешает создать аккаунт, но не позволяет
включить публикацию или откликнуться. Согласие можно сохранить/отозвать в
раскрываемом блоке редактирования профиля. Публикация сохраняет отдельное
согласие и время; время согласий всегда реальное.

Отзыв обработки скрывает профиль, отзывает публикацию и запрещает дальнейшее
раскрытие контактов/полного PDF работодателям. Для прежних принятых Offer,
у которых нет новой записи согласия, сохранён прежний контракт до явного
отзыва. Принятое приглашение разрешает контакты только его компании.
Самостоятельный отклик требует отдельный checkbox передачи контактов
именно компании вакансии. Сообщения и встречи разрешены только этой паре.

## Минимальные исправления прежней логики: было / стало

### Провал добровольной проверки не отменяет подтверждённый грейд

Было в assessments/service.py:

```python
session.execute(update(CandidateCategory)
    .where(CandidateCategory.candidate_profile_id == candidate_profile_id,
           CandidateCategory.is_current.is_(True)).values(is_current=False))
# новая запись
is_current=True
```

Стало:

```python
becomes_current = passed or confirmed is None
if becomes_current:
    session.execute(update(CandidateCategory)
        .where(CandidateCategory.candidate_profile_id == candidate_profile_id,
               CandidateCategory.is_current.is_(True)).values(is_current=False))
# новая запись
is_current=becomes_current
```

Провальная попытка остаётся в истории. Прежние кулдауны и лимиты сохранены.

### Повтор ответа и завершения

Было: повторный ответ перезаписывал answer/is_correct. Завершённая попытка
в finish_attempt вызывала AttemptAlreadyCompleted — это корректное прежнее
поведение сохранено (API 409, HTML перенаправляет к прежнему результату).

Стало:

```python
if answer.answered_at is not None:
    if answer.answer == answer_payload:
        return answer
    raise InvalidAnswer("Ответ уже сохранён; изменить его нельзя")
if attempt.status == AttemptStatus.COMPLETED:
    raise AttemptAlreadyCompleted()  # прежний контракт сохранён
```

Повтор не создаёт категории и не изменяет результат. Публичная выдача по-
прежнему скрывает correct/is_correct до завершения. HTML теперь умеет
передавать multiple_choice как values; прежний single_choice/value сохранён.

### Структура вариантов

Было: `chosen = rng.sample(pool, QUESTIONS_PER_ATTEMPT)`.

Стало: `chosen = structured_sample(pool, QUESTIONS_PER_ATTEMPT, rng)`.

Квоты по topic/type/difficulty выбираются устойчивым обходом; внутри групп
вопросы и итоговый порядок случайны. Состав/варианты/правильный ответ
сохраняются прежними снимками на сервере. Структура сопоставима в пределах
неизменного банка, не является доказанной психометрической калибровкой.

Формула процента уже была исправлена ранее и сохранена:
`round(correct / assigned_total * 100)`. difficulty не является весом.
Оценены точные 0/10, 1/10, 5/10, 9/10, 10/10 и 3/4; 9/10 показан в Chromium.

### Публикация и контакты

К существующему set_publication добавлены проверка подтверждения email,
согласия обработки и сохранение согласия публикации. К прежней сериализации
контактов принятого Offer добавлена проверка явного отзыва обработки.
Контракты и статусы Offer не менялись. Генератор PDF не переписывался.

## Временные правила

- VACANCY_EDIT_DAYS=14: существенные поля (роль, специализация, грейд,
  навыки, формат) после периода фиксируются; описание, условия, зарплата,
  способ связи редактируются постоянно.
- VACANCY_LIFETIME_DAYS=30: отдельный срок публикации.
- VACANCY_REPOST_DAYS=30: удалённая аналогичная роль блокирует пересоздание.
  Аналогичность: нормализованные название + специализация + грейд у той же
  компании, того же типа. Другие роли не блокируются.
- VACANCY_ACTIVITY_THRESHOLD=1: после первоначального периода продление /
  восстановление требует хотя бы один рассмотренный отклик данной вакансии.
- Продление добавляет срок к max(now, expires_at), не меняет created_at и
  не открывает новый период редактирования требований.
- new → stable после 14 дней; new/stable → inactive по expires_at.
  deleted — отдельный архив, восстановлению не подлежит.
- INTERVIEW_AUTO_DAYS=2: начало — более позднее из времени встречи и
  заявления работодателя, что встреча состоялась. При возражении кандидата
  автоподтверждения нет. До истечения срока кандидат видит событие и действие.
- Найм никогда не подтверждается перемоткой: нужны обе стороны отдельно.

Один process_due вызывается страницами, demo и штатным фоновым потоком
app.start раз в 60 секунд. Также доступен `python -m app.scripts.process_events`.
Повторная обработка идемпотентна. Даты новых бизнес-событий используют тот же
источник времени. JWT/cookies, email-токены, даты юридических согласий не
переводились на эти часы.

## Запуск для жюри

Обычный режим, PowerShell из корня:

```powershell
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
docker compose up -d --build
docker compose ps
```

Приложение http://localhost:8000; Mailpit http://localhost:8025.
Миграции и заполнение пустого банка запускаются app.start. Изменённый банк
на перезапуске не перезаписывается. Ссылки писем используют APP_BASE_URL;
для внешнего адреса задайте его в .env. Внутренний http://app:8000 не используется.
Реальный почтовый ящик не нужен: регистрация → Mailpit → открыть письмо →
перейти по ссылке подтверждения → войти. Подтверждение не отключается.

Отдельный demo-стенд (НЕ объединять с обычным compose.yaml):

```powershell
$env:DEMO_MOCK_KEY = [guid]::NewGuid().ToString('N')
$env:DEMO_JWT_SECRET = [guid]::NewGuid().ToString('N') + [guid]::NewGuid().ToString('N')
docker compose -p fspcareer-demo -f compose.demo.yaml up -d --build
```

Приложение http://localhost:8002; Mailpit http://localhost:8027.
Создайте аккаунт оператора обычной регистрацией и подтвердите через Mailpit.
Узнайте собственный ID через GET /api/v1/auth/me в авторизованном браузере.
Разрешите именно его (пример — ID 1):

```powershell
$env:DEMO_OPERATOR_IDS = '1'
docker compose -p fspcareer-demo -f compose.demo.yaml up -d --no-deps app
```

DEMO_MODE включён только в этом файле. Settings запрещает demo на обычной
БД: используется fspcareer_demo и отдельный project/volume. Оператор —
подтверждённая серверная сессия + явный список ID, не отдельная роль с
обходом auth. DEMO_MOCK_KEY — служебный серверный ключ между приложением и
mock, не показывается в UI. Сохраните выбранный ключ для последующих команд.
Без operator IDs просмотр разрешён, изменения запрещены. В обычном режиме
POST служебных маршрутов возвращает 404; в demo обычным участникам — 403.
DEMO_JWT_SECRET обязателен и отличается от обычного стенда: открытый
фиксированный ключ не используется для сессий оператора. Сохраните оба
сгенерированных значения для последующих команд того же окружения.

Mock-изменения сохраняются в demo_registry:/data/registry.sqlite и читаются
тем же API адаптеров. Наборы не создаются автоматически. На /design-preview
явно задайте пароль подготовленных аккаунтов и нажмите «Создать набор».
Вы увидите их тестовые email; используйте указанный пароль для входа.
Подтверждённые аккаунты и категория набора — маркированные тестовые фикстуры,
а не сценарий проверки регистрации/экзамена. Регистрацию показывайте отдельно.

Порядок демонстрации:

1. Реальные две роли: регистрация/письмо/подтверждение → профиль → тест →
   категория → публикация → потребность → подбор → прямое приглашение →
   принятие → контакты и общение.
2. Вакансия → самостоятельный отклик с согласием → рассмотрение → события
   и место компании в рейтинге → встреча → подтверждения собеседования/найма.
3. Demo-набор → +2 дня (стабильная/истёкшая вакансия и собеседование) →
   попытка восстановления с недостаточной/достаточной активностью →
   редактирование после срока → архив и запрет повторной аналогичной роли.
4. Участник mock и достижение (создаются и набором) → привязка ID в кабинете
   кандидата → импорт → обновление без дублей → достижение в профиле и PDF.

Часы общие для ВСЕГО стенда. Сброс часов не откатывает переходы и не обещает
изолированное время одного сценария. Удаление набора касается его аккаунтов,
их взаимодействий и записей mock с ID этого набора, не других пользователей.
Ручные записи mock вне набора сохраняются. Обычная БД не наполняется демо.

PostgreSQL 17. Service/API-фикстуры создавали свои временные БД в нём;
