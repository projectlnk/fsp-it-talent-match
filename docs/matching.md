# Механика подбора и ранжирования

## Задача

Существующие площадки поиска работы устроены одинаково: кандидат откликается
на вакансию, работодатель вручную фильтрует десятки нерелевантных откликов.
Универсальные job-борды не формализуют ИТ-специфику — стек, грейд, роль —
поэтому релевантность выдачи низка с обеих сторон.

Наша платформа меняет механику: **инициатива исходит от работодателя**.
Кандидат не откликается — он становится виден в категории, а работодатель
сам находит нужную категорию и адресно приглашает конкретного человека
с указанием зарплаты.

Это смысловой центр решения и главный критерий оценки.

## Категоризация

Категория кандидата — связка **специализации и грейда**:

- `specialization` — backend, frontend (расширяется).
- `grade` — intern, junior, middle, senior.

Категория присваивается **по результату теста**, а не по самоописанному
резюме. Это прямая фиксация из ТЗ и Q&A:

> Грейд соискатель может выбрать сам, но если не прошел тест, можно добавить
> статус «грейд не подтверждён», «официально» грейд присваивается только
> по результату тестирования — это основа всей механики.

Достижения ФСП **не влияют на грейд** — только на ранжирование внутри
категории.

## Поиск: что видит работодатель

Работодатель открывает `/employer/search` и задаёт фильтры:

- специализация,
- грейд,
- навыки (через запятую, регистронезависимо),
- наличие достижений ФСП.

По умолчанию показываются только кандидаты с **подтверждённой**
категорией. Неподтверждённые видны только при явном запросе
(`only_confirmed=false`) — это соответствует рекомендации Q&A:
«неподтверждённый грейд лучше показывать со статусом и опускать
в выдаче, не скрывать полностью».

### Карточка кандидата

В карточке кандидата работодатель видит:

- ФИО и локацию,
- желаемую роль и зарплатные ожидания,
- специализацию и грейд,
- **рейтинг и причины попадания в топ**,
- навыки,
- места работы,
- достижения ФСП (личные и командные, с пометкой «демо»).

**Контакты не показываются.** Email и телефон скрыты до момента, когда
кандидат принял приглашение или сам откликнулся.

## Формула ранжирования

Внутри категории кандидаты сортируются по `ranking_score` от 0 до 100:

```
ranking_score = 100 * (
    0.70 * test_component
  + 0.20 * fsp_component
  + 0.10 * relevance_component
)
```

### 1. Результат теста — 70%

```
test_component = test_score / 100
```

Доминирующий сигнал. По Q&A грейд присваивает только тест, и достижения
не заменяют его. Вес 70% гарантирует, что кандидат с высоким test_score
оказывается выше кандидата с большим числом достижений, но слабым тестом.

### 2. Достижения ФСП — 20%

```
fsp_component = min(1.0, Σ weight_i / 5.0)
```

Вес одного достижения:

```
weight = place_weight × freshness_weight
```

- `place_weight`:
  - 1 место — 1.0
  - 2 место — 0.7
  - 3 место — 0.5
  - разряд — 0.5
  - просто участие — 0.2
- `freshness_weight`:
  - достижение за последние 2 года — 1.0
  - старше 2 лет — 0.5

**Diminishing returns:** максимум достигается на 5 «полновесных»
достижениях. Дальнейший рост не увеличивает компонент. Это защита от
«накрутки» профиля множеством простых участий.

### 3. Релевантность дисциплины — 10%

```
relevance_component = (relevant_count / total_count)
```

где `relevant` — достижения, у которых `discipline_code` совпадает с
кодом специализации кандидата.

Идея из Q&A:

> Если один специалист по ИБ участвовал в соревнованиях по ИБ, это будет
> релевантнее, чем когда другой специалист по ИБ участвовал в соревнованиях
> по робототехнике.

## Объяснимость выдачи

Ключевое требование ТЗ: работодатель должен видеть, **почему** кандидат
попал в топ, а не только его место в списке.

Каждая карточка в выдаче содержит поле `ranking_reasons` — массив
человекочитаемых строк:

- «Результат теста: 85%»
- «Достижения ФСП: призовых мест: 2, разрядов: 1»
- «Релевантных дисциплине "backend" достижений: 2»

Пример карточки в API:

```json
{
  "profile_id": 42,
  "full_name": "Иван Иванов",
  "specialization_code": "backend",
  "grade_code": "junior",
  "test_score": 85,
  "ranking_score": 79.5,
  "ranking_reasons": [
    "Результат теста: 85%",
    "Достижения ФСП: призовых мест: 2",
    "Релевантных дисциплине «backend» достижений: 2"
  ]
}
```

## Приглашение кандидату

Приглашение (`Offer`) — это адресное предложение конкретному кандидату.
**Привязка к опубликованной вакансии не требуется** — это прямо следует
из ТЗ. Работодатель описывает предложение, указывает зарплату и способ
связи, отправляет.

### Обязательные поля

- `title` — заголовок предложения.
- `description` — описание.
- `salary_from`, `salary_to` — диапазон зарплаты, **обязательно**.
- `salary_gross` — gross или net (принципиально подписать).
- `contact_method` — способ связи, который работодатель готов раскрыть
  кандидату сразу.

### Статусы

- `sent` — отправлено, кандидат ещё не открывал.
- `viewed` — кандидат открыл карточку.
- `accepted` — кандидат принял приглашение.
- `rejected` — кандидат отклонил.

Переходы:

- `sent → viewed` — при первом открытии кандидатом.
- `sent/viewed → accepted` — по решению кандидата.
- `sent/viewed → rejected` — по решению кандидата.
- Повторный ответ невозможен.

## Правила видимости контактов

Принципиальное условие ТЗ:

> Контактные данные кандидата раскрываются работодателю только после
> того, как кандидат принял приглашение или откликнулся сам.

В нашем решении:

- **В поиске и в карточке контактов нет.** Даже если кандидат в базе —
  работодатель видит ФИО, места работы, навыки, достижения, но не email
  и не телефон.
- **В приглашении `contacts` — `null`**, пока статус не `accepted`.
- **После `accepted`** — работодатель видит email и телефон в карточке
  приглашения.
- **При `rejected`** — контакты не раскрываются никогда.

Реализовано на уровне сервиса: `_to_offer_read(reveal_contacts=...)`
заполняет поле только при `status == accepted`. Это исключает случайную
утечку через сериализацию.

## Изоляция доступа

- **Работодатель** видит только свои приглашения. При попытке открыть
  чужое — `404` (не `403`, чтобы не светить факт существования).
- **Кандидат** видит только адресованные ему приглашения.
- **Поиск** доступен только роли `employer`, кандидаты получают `403`.
- **Ручки кандидата** (`/candidates/me/offers`) защищены ролью `candidate`.

Всё это проверено интеграционными и e2e тестами.

## Пагинация и производительность

- Лимит страницы — 20 (настраивается до 100).
- Сортировка рейтинга выполняется в Python после загрузки связанных
  сущностей: формула зависит от достижений ФСП и релевантности, её сложно
  выразить в SQL без дублирования логики.
- Связанные сущности (навыки, опыт, достижения) загружаются одним
  запросом через `selectinload` — N+1 исключён.

Для больших баз рейтинг выносится в materialized view или вычисляется
фоновым процессом. На MVP с сотнями кандидатов пагинация по 20 элементов
сортируется в памяти мгновенно.

## Ограничения MVP

- **2 специализации** (backend, frontend) × 4 грейда. Расширение —
  добавление строк в справочник.
- **Нет публикации вакансий и откликов кандидатов.** Это дополнительный
  сценарий, не ядро. Может быть добавлен после хакатона.
- **Нет интеграции с ATS.** Концепция описана отдельно.
- **Нет чата на платформе.** После принятия контакты раскрываются, общение
  идёт по указанному работодателем способу связи.

## План валидации

По ТЗ и Q&A команда сама предлагает процедуру валидации. Мы валидируем
три аспекта.

### 1. Разделяющая сила ранжирования

Готовим синтетический датасет:

- 100 кандидатов с разными `test_score` (от 30 до 100).
- У 50% есть достижения ФСП разного уровня (1 место / 3 место / участие).
- Дисциплины достижений: у половины релевантные специализации, у половины —
  нет.

Ожидаемое поведение:

- Кандидат с `test_score=100` без ФСП должен быть выше кандидата с
  `test_score=50` и пятью 1-ми местами. Проверяет доминирование теста.
- При равном `test_score` кандидат с 1 местом выше кандидата с участием.
  Проверяет вес места.
- При равном тесте и равных местах кандидат с релевантной дисциплиной
  выше. Проверяет компонент релевантности.

### 2. Объяснимость

Каждая карточка в выдаче должна иметь непустой `ranking_reasons`.
Проверяется автоматически в интеграционных тестах: если карточка есть,
`ranking_reasons` — не пустой список.

### 3. Правила видимости

- Ни одна карточка в поиске не содержит `phone` или `email`.
- `contacts` в приглашении заполнены только при `status=accepted`.
- После `rejected` контакты не раскрываются.

Всё это покрыто тестами:

- `tests/integration/test_matching_service.py`
- `tests/integration/test_matching_api.py`
- `tests/integration/test_offers_service.py`
- `tests/integration/test_offers_api.py`
- `tests/e2e/test_matching_flow.py`

### 4. Ручная проверка жюри

Сквозной сценарий, который жюри может пройти:

1. Зайти кандидатом, пройти тест, получить категорию.
2. Зайти работодателем, найти категорию, открыть карточку.
3. Убедиться, что контактов нет.
4. Отправить приглашение с зарплатой.
5. Зайти кандидатом, увидеть приглашение, принять или отклонить.
6. Зайти работодателем, увидеть контакты (если принято) или их отсутствие
   (если отклонено).

## Соответствие критериям оценки

| Критерий | Как закрыт |
| --- | --- |
| Оригинальность механики | Работодатель ищет по категориям, приглашает адресно |
| Работоспособность | Сквозной сценарий покрыт e2e-тестом |
| Практическая применимость | Обе стороны видят условия до контакта |
| Обоснованность ранжирования | Формула 70/20/10 с обоснованием из Q&A |
| Объяснимость выдачи | `ranking_reasons` в каждой карточке |
| Релевантность топа | Разделяющая сила по тесту выше, чем по достижениям |
| Реальный сценарий | Работодатель описывает потребность, получает подборку |
