# Интеграция с ФСП ID

## Что такое ФСП ID

Единый аккаунт участника на ресурсах Федерации спортивного программирования.
Задуман как точка входа и источник **подтверждённых достижений**: участий,
мест, разрядов, дисциплин, командных результатов.

На момент хакатона:
- боевой API не предоставляется;
- описание схемы данных не выдаётся;
- Keycloak как основа FSP ID существует, но боевых доступов нет.

## Как устроена интеграция в решении

### Два независимых направления

Мы разделяем **идентификацию** и **данные реестра**.

- **Идентификация** — подтверждение, что пользователь платформы является
  владельцем аккаунта ФСП ID. Реализуется через OAuth 2.0 / OpenID Connect,
  в будущем — через Keycloak.
- **Реестр достижений** — отдельный API, отдающий список результатов
  участия. Доступен по внутреннему идентификатору участника.

В боевой системе это **разные сервисы**. Поэтому в нашем решении это
разные адаптеры и разные таблицы в БД:

- `external_identities` хранит пару `(issuer, sub)` — кто пользователь
  в конкретном провайдере идентификации.
- `fsp_registry_links` хранит `registry_participant_id` — идентификатор
  участника именно в реестре ФСП.

Это соответствует требованиям Q&A: «отдельно реализовать тестовую привязку
личности/участника и импорт; хранить ID реестра отдельно от `(issuer, sub)`».

### Адаптеры

В `app/integrations/fsp/` два интерфейса:

- `IdentityProvider.get_profile(participant_id)` — профиль участника.
- `AchievementRegistry.get_achievements(participant_id)` — список достижений.

Текущие реализации — `FspIdentityClient` и `FspRegistryClient` —
обращаются к локальному моку `mini-fsp-id` по HTTP.

### Мок-сервис `mini-fsp-id`

Отдельный FastAPI-сервис в Compose, доступный на `http://mini-fsp-id:8000`
внутри сети и на `http://localhost:8001` с хоста.

Эндпоинты:
- `GET /participants` — список участников.
- `GET /participants/{id}` — профиль.
- `GET /participants/{id}/achievements` — достижения.

Данные лежат в `mock_fsp/data/*.json`. Все достижения помечаются
флагом `is_demo=True` при импорте — в UI показывается бейдж «демо».

`demo-2` намеренно оставлен без достижений — край-кейс из ТЗ
(«корректная обработка кандидата без истории ФСП»).

## Что происходит при привязке

1. Кандидат в профиле вводит `participant_id` (в демо — из подсказки).
2. Платформа вызывает `IdentityProvider.get_profile` и
   `AchievementRegistry.get_achievements`.
3. Если участник не найден — 404, в UI красный алерт.
4. Если `participant_id` уже привязан к другому профилю — 409,
   защита от коллизий.
5. Сервис `link_and_import_fsp`:
   - сохраняет или обновляет запись `fsp_registry_links`;
   - идемпотентно делает upsert достижений по `external_achievement_id`;
   - помечает все импортированные достижения `is_demo=True`.
6. UI показывает достижения с бейджем «демо» и «командное» (если `is_team`).

## Правила ранжирования

Достижения ФСП **не влияют на грейд**. Это прямая фиксация из Q&A:
грейд присваивает только первичный тест.

Достижения учитываются в ранжировании внутри категории
(см. `docs/matching.md`). Релевантность дисциплины специализации
кандидата может давать небольшой дополнительный вес — идея из Q&A.

## Защита от ошибок

- **Проверка `response_id == participant_id`.** Защита от подмены ответа
  реестра.
- **Уникальность `registry_participant_id`.** Один участник ФСП не может
  быть привязан к двум профилям.
- **Идемпотентный импорт.** Повторный импорт обновляет поля, а не создаёт
  дубли, по ключу `(candidate_profile_id, external_achievement_id)`.
- **Каскадная отвязка.** `unlink_fsp` удаляет связь и импортированные
  достижения одной транзакцией.
- **Корректная обработка «нет истории».** Кандидат без ФСП ID полноценно
  пользуется платформой.

## Переход на боевую интеграцию с Keycloak

Ожидаемый путь после хакатона:

1. **Авторизация.**
   - В Keycloak регистрируется клиент платформы.
   - Платформа получает `client_id`, `client_secret`, `issuer URL`.
   - Добавляется маршрут `/auth/callback`, использующий OAuth 2.0
     Authorization Code Flow с PKCE.
   - После успешной аутентификации в `external_identities` сохраняется
     пара `(issuer=<issuer URL>, sub=<полученный sub>)`.

2. **Данные реестра.**
   - Реальный API ФСП предоставляет метод получения достижений по
     `participant_id`.
   - Заменяется реализация `AchievementRegistry` — с
     `FspRegistryClient` (HTTPX к моку) на клиент боевого API.
   - Контракт импорта (`link_and_import_fsp`) остаётся неизменным.

3. **Конфигурация.**
   - `FSP_BASE_URL` — адрес реального реестра.
   - `KEYCLOAK_ISSUER`, `KEYCLOAK_CLIENT_ID`, `KEYCLOAK_CLIENT_SECRET` —
     параметры OIDC-клиента.

4. **Совместимость.**
   - Модели данных уже поддерживают будущую интеграцию.
   - Мок-сервис остаётся для локальной разработки и тестов
     (`FSP_MODE=mock`).
   - Адаптеры заменяются без переписывания бизнес-логики.

## Что не делаем на MVP

- Реальный Keycloak в Docker Compose.
- Полноценный OIDC-флоу с редиректами.
- Синхронизацию по расписанию (данные импортируются по запросу
  пользователя).
- Автоматическую проверку достижений на подлинность (это делает реестр).
