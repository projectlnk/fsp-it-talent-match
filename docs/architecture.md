# Архитектура решения

## Общая схема

```
┌──────────────┐       ┌────────────────────┐       ┌──────────────┐
│  Браузер     │──────▶│  FastAPI (app)     │──────▶│ PostgreSQL   │
│  (HTML+HTMX) │       │  JSON API + Jinja2 │       │              │
└──────────────┘       └────────────────────┘       └──────────────┘
                                │
                                ▼
                       ┌────────────────────┐
                       │  mini-fsp-id (мок) │
                       │  ФСП ID и реестр   │
                       └────────────────────┘
```

Все сервисы работают в Docker Compose:

- `app` — FastAPI, JSON API и HTML-страницы.
- `db` — PostgreSQL.
- `mini-fsp-id` — локальный мок FSP ID.
- `mailpit` — SMTP-сервер для демонстрации писем.

## Модульный монолит

Архитектура — **модульный монолит** с чёткими границами. Микросервисы
не используются: для MVP это избыточно, а слабая связанность модулей
позволяет вынести любой из них позже.

```
app/
├── main.py              FastAPI-приложение
├── start.py             ожидание БД, миграции, Uvicorn
├── core/                конфиг, отправка email
├── db/                  Base, сессия, агрегатор моделей
├── api/                 корневой API-роутер
├── web/                 корневой web-роутер
├── modules/
│   ├── auth/            пользователь, регистрация, роли
│   ├── candidates/      профиль кандидата, ФСП ID
│   ├── employers/       профиль компании, приглашения
│   ├── assessments/     тесты, категории, кулдаун
│   └── matching/        поиск, ранжирование
├── integrations/fsp/    адаптеры ФСП ID
├── templates/           Jinja2-шаблоны
└── static/              CSS, JS, HTMX
```

### Внутренняя структура модуля

Каждый модуль содержит:

- `models.py` — SQLAlchemy-модели.
- `schemas.py` — Pydantic-схемы (JSON API и валидация).
- `service.py` — бизнес-логика. **Сервис не знает про HTTP.**
- `router.py` — JSON API.
- `web.py` — HTML-страницы (если есть).
- `dependencies.py` — FastAPI-зависимости (только в auth).

**Разделение ответственности:**

- **Роутер** принимает HTTP, вызывает сервис, транслирует ошибки в коды.
- **Сервис** знает про БД, не знает про FastAPI.
- **Модель** описывает таблицу.
- **Схема** — контракт для API.

Это даёт:

- сервисы тестируются без поднятия HTTP;
- одна логика для JSON API и HTML;
- при переезде на Keycloak меняется только роутер или адаптер.

## Слои

### Auth

- JWT в httpOnly cookie или `Authorization: Bearer`.
- `get_current_user` — читает токен, проверяет подпись, достаёт пользователя.
- `require_role(...)` — фабрика зависимостей для ролевого доступа.
- `ExternalIdentity(issuer, sub)` — заготовка под Keycloak.

### Candidates

- `CandidateProfile` — ФИО, контакты, желаемые условия.
- `CandidateSkill`, `CandidateExperience` — стек и опыт.
- `FspRegistryLink`, `FspAchievement` — связь с реестром ФСП.
- Сервис — только БД. HTTP-вызовы к FSP ID делает роутер.

### Employers

- `EmployerProfile` — компания.
- `Offer` — адресное приглашение с зарплатой и статусами.
- Раскрытие контактов — только при `status=accepted`.

### Assessments

- Справочники `Specialization`, `Grade`, `Category`.
- `Question` — параметризованный шаблон.
- `TestAttempt`, `TestAnswer` — попытки и снапшоты вопросов.
- `CandidateCategory` — текущий подтверждённый статус, история.
- `GradeChangeCooldown` — кулдаун смены грейда.

### Matching

- Своих таблиц нет — работает по данным других модулей.
- `ranking.py` — чистые функции ранжирования.
- `service.py` — фильтры, пагинация, объяснимость.

## Поток данных

### Регистрация → тест → категория

1. Пользователь регистрируется, создаётся `User` + профиль по роли.
2. Письмо с подтверждением уходит через Mailpit.
3. Кандидат проходит тест: `start_attempt` выбирает 10 шаблонов,
   инстанцирует, сохраняет снапшоты в `TestAnswer`.
4. `finish_attempt` считает взвешенный счёт, создаёт `CandidateCategory`.
5. При успехе ставится кулдаун `GradeChangeCooldown`.

### Поиск → приглашение → раскрытие

1. Работодатель вызывает `/api/v1/matching/candidates` с фильтрами.
2. Сервис выбирает кандидатов по текущим категориям, ранжирует в Python.
3. Карточка содержит `ranking_reasons`, но без контактов.
4. `create_offer` создаёт `Offer` со статусом `sent`.
5. Кандидат открывает — статус `viewed`.
6. Принимает — `accepted`, контакты раскрываются работодателю.
7. Отклоняет — `rejected`, контакты не раскрываются никогда.

## Интеграция с ФСП ID

Два независимых направления:

- **Идентификация** — `(issuer, sub)` в `external_identities`.
  В будущем — OAuth 2.0 / OIDC через Keycloak.
- **Реестр достижений** — `registry_participant_id` в `fsp_registry_links`.
  В будущем — боевой API ФСП.

Подробнее — [fsp-integration.md](fsp-integration.md).

## Безопасность

- Пароли — bcrypt с SHA-256 пре-хешем (обход лимита 72 байта).
- JWT — HS256, срок 24 часа.
- httpOnly cookie + защита от open redirect.
- Разграничение прав по ролям через `require_role`.
- Изоляция данных: пользователь видит только своё.
- Согласие на обработку ПДн при регистрации (152-ФЗ).
- Контакты кандидата скрыты до принятия приглашения.

## База данных

18 таблиц. Миграции — Alembic, naming convention задана в `base.py`.

Ключевые решения:

- `is_current` в `candidate_categories` — текущая категория, история
  сохраняется.
- Уникальность `(candidate_profile_id, external_achievement_id)` —
  идемпотентный импорт достижений.
- Уникальность `(issuer, sub)` в `external_identities` — защита от коллизий.
- `ondelete="CASCADE"` там, где зависимость логична.

## Тестирование

- **Unit** (`tests/backend`) — без БД и HTTP: ранжирование, схемы,
  криптография.
- **Integration** (`tests/integration`) — против запущенного Compose:
  реальная БД, HTTP, мок FSP ID, Mailpit.
- **E2E** (`tests/e2e`) — Playwright: сквозные сценарии через браузер.

E2E-тесты запускаются с хоста и не имеют прямого доступа к БД. Для
подготовки данных используется CLI-хелпер `app.scripts.grant_category`,
вызываемый через `docker compose exec`.

## Расширение

### Добавление специализации

1. Строка в `specializations`.
2. Миграция с сидом.
3. Шаблоны вопросов в `app/modules/assessments/seed/`.

Кода менять не нужно.

### Добавление нового модуля

1. Создать `app/modules/<name>/` с `models.py`, `schemas.py`, `service.py`,
   `router.py`.
2. Импортировать модели в `app/db/models.py`.
3. Подключить роутер в `app/api/router.py`.
4. Сгенерировать миграцию.

### Интеграция с ATS

По ТЗ — концепция, не MVP. Точка расширения: `employers/service.py`,
функции работы с `Offer`. Адаптер к ATS добавляется как
`app/integrations/ats/` без изменения бизнес-логики.

## Ограничения MVP

- Keycloak не развёрнут: имитация привязки к FSP ID.
- Нет публикации вакансий и откликов кандидатов.
- Нет чата и календаря собеседований.
- Нет интеграции с ATS.
- Ранжирование сортируется в Python: для больших баз нужно вынести в SQL.
