# FSP IT Talent Match

<<<<<<< Updated upstream
Цифровая платформа-агрегатор ИТ-вакансий с верифицированным профилем
достижений участника Федерации спортивного программирования.

Прототип разработан в рамках хакатона «Лидеры цифровой трансформации 2026».

## О задаче

Существующие площадки поиска работы универсальны и не решают задачу
релевантного подбора в ИТ. Работодатель тонет в нерелевантных откликах,
кандидат откликается вслепую и не получает обратной связи.

Платформа меняет механику: **инициатива исходит от работодателя**.
Кандидат проходит обязательное тестирование, получает категорию
«специализация + грейд» и становится виден в ранжированной выдаче.
Работодатель описывает потребность, получает объяснимую подборку и
отправляет адресное приглашение с указанием зарплаты. Контакты
раскрываются только после принятия приглашения.

## Ключевые особенности

- **Два ролевых кабинета:** кандидат и работодатель.
- **Обязательное тестирование:** опрос, выбор грейда, тест.
- **Автоматическая категоризация:** специализация + подтверждённый грейд.
- **Антиутечка заданий:** параметризованные шаблоны вопросов, случайная
  выборка и порядок вариантов.
- **Взвешенный подсчёт** с разделяющей силой: сложные вопросы весят больше.
- **Объяснимый подбор:** работодатель видит, почему кандидат в топе.
- **Адресное приглашение:** без обязательной привязки к вакансии, с
  зарплатой и описанием предложения.
- **Правила видимости:** контакты открываются только после принятия.
- **Интеграция с ФСП ID:** имитация привязки, мок-сервис достижений и
  скелет будущей интеграции с Keycloak.
- **Обработка кандидата без истории ФСП.**

## Технологии

- **Backend:** FastAPI, SQLAlchemy 2.0, Alembic, PostgreSQL, Pydantic v2.
- **Frontend:** Jinja2, HTMX, ванильный CSS.
- **Auth:** JWT в httpOnly cookie, bcrypt.
- **Инфраструктура:** Docker Compose (app, db, mini-fsp-id, mailpit).
- **Тесты:** pytest, pytest-playwright.

## Быстрый старт

Нужен только Docker с Compose v2.

```bash
cp .env.example .env
docker compose up --build
```

После запуска:

- Приложение: http://localhost:8000
- Swagger: http://localhost:8000/docs
- Мок FSP ID: http://localhost:8001/docs
- Mailpit (почта): http://localhost:8025

### Регистрация и подтверждение email для жюри

После скачивания репозитория скопируйте `.env.example` в `.env`
(`cp .env.example .env`; в PowerShell — `Copy-Item .env.example .env`)
и выполните `docker compose up --build`. Дождитесь готовности приложения.

1. Откройте http://localhost:8000/auth/register и зарегистрируйте кандидата,
   например с адресом `jury@example.com`, указав имя и пароль от 8 символов.
2. Откройте http://localhost:8025 — Mailpit принимает письма локально.
3. Найдите письмо «Подтверждение email — FSP IT Talent Match» для этого адреса
   и нажмите «Подтвердить email». Ссылка ведёт на `http://localhost:8000/auth/verify`;
   вручную исправлять её не нужно.
4. После сообщения об успешном подтверждении откройте
   http://localhost:8000/auth/login и войдите с указанными email и паролем.

Реальный почтовый ящик не нужен: Mailpit не отправляет письма во внешнюю почту.
Используйте новый адрес для каждой регистрации, если аккаунт уже существует.
Для другого порта или внешнего адреса задайте `APP_BASE_URL` в `.env`
(например, `http://localhost:8080` вместе с `APP_PORT=8080`).
Внутренний адрес `http://app:8000` для ссылок в письмах использовать нельзя.

## Сквозной сценарий

1. Кандидат регистрируется, подтверждает email, проходит тест на грейд.
2. Система присваивает категорию: специализация + подтверждённый грейд.
3. Работодатель ищет кандидатов по фильтрам, видит рейтинг и причины.
4. Работодатель отправляет адресное приглашение с зарплатой.
5. Кандидат принимает или отклоняет.
6. При принятии контакты кандидата раскрываются работодателю.

Связи файлов:

- Браузер → `app/web/router.py` → модульный `web.py` → схемы/`service.py` → SQLAlchemy через `app/db/session.py` → PostgreSQL → Jinja2 → HTML.
- API → `app/api/router.py` → модульный `router.py` → зависимости пользователя/роли → схемы/`service.py` → БД → JSON.
- Модели модулей → `app/db/models.py` → `Base.metadata` → `migrations/env.py` → Alembic → ревизии → PostgreSQL.
- Будущая привязка/импорт → сервис кандидата и auth → `identity.py` / `registry.py` → `mini-fsp-id` → сохранение результата. Эта пользовательская цепочка пока не подключена.

`models.py` описывает таблицы; `schemas.py` — входы/выходы и валидацию; `service.py` — правила и транзакции; `router.py` — JSON HTTP; `web.py` — HTML HTTP; шаблоны — отображение. HTML-формы должны использовать согласованную серверную валидацию, как API. Простые запросы остаются в сервисе; для поиска можно добавить `queries.py`, когда это улучшит читаемость.

Общие точки подключения: `app/api/router.py`, `app/web/router.py`, `app/db/models.py`, `app/templates/base.html`. Изменения здесь и порядок миграций согласовывать между разработчиками. Не создавать заново реализованные профили и auth.

## Найденные проблемы

1. **Общий JS:** `app/static/js/main.js` обращается к `#js-status` без проверки наличия. Элемент есть только на главной; на auth-страницах воспроизведено `Cannot set properties of null`.
2. **Валидация:** HTML-регистрация и формы профилей обходят схемы API. Неверные числа/даты могут превращаться в `None`. PATCH проверяет присланные поля без достаточной проверки итогового состояния: воспроизведён диапазон зарплаты 200–150; update опыта принимает начало позже окончания; `full_name: null` и дублирующее имя навыка приводят к необработанному `IntegrityError`.
3. **Email:** вход разрешён до подтверждения, хотя комментарий API обещает обратное. Правило нужно согласовать, затем привести код и сообщения к одному поведению. Повторная отправка письма сейчас доступна через API.
4. **Вопрос теста:** `sql_group_by` в `app/modules/assessments/seed/backend_junior.json` хранит правильный ответ `COUNT`, но варианты в UI — текстовые объяснения. Через UI правильно ответить невозможно; тест, подставляющий ответ из snapshot, скрывает дефект.
5. **Вопросы при запуске:** startup и Compose не вызывают `seed_loader`. На новой БД после миграций вопросы нужно загружать отдельно. Команда загрузки пока не зафиксирована в инструкции; нельзя считать один `docker compose up` готовым запуском тестирования.
6. **Категории:** провал заменяет текущую категорию; проверка cooldown зависит от текущего `CONFIRMED`, что создаёт путь обхода. Подсчёт провалов охватывает всю историю; допускаются активные попытки разных пар специализация/грейд. Атомарность старта и единственной текущей категории не обеспечена. Возможность гонки выявлена по коду, конкурентный прогон не проведён. Фраза «попытка не сгорает» расходится с подсчётом провалов.
7. **Миграции:** `question_snapshot NOT NULL` добавляется без переноса существующих ответов. Миграционный default `answered_at` расходится с ORM, который вставляет `NULL`; это расхождение, а не доказанная поломка запуска. Переход БД со старой удалённой `0001_initial` не проверен.
8. **Изоляция тестов:** integration использует `SessionLocal` приложения; данные создаются и удаляются по email-префиксу. Это не гарантирует отдельную БД. Auth E2E создаёт данные без очистки.

Ошибки сервиса профиля воспроизведены на отдельной SQLite в памяти. Это полезные регрессии, но не подтверждение поведения PostgreSQL.

## Что нужно согласовать

- Разрешён ли вход до подтверждения email и какие операции доступны такому пользователю.
- Пороги категории, судьба подтверждённой категории после провала, область cooldown, период подсчёта провалов, число одновременных попыток. В коде есть **70%/40%, 60 дней и три провала**, но аудит не нашёл документального подтверждения согласования.
- Поля профиля, видимые работодателю, и точные фильтры поиска.
- Контракт демо-привязки личности/реестра и доказательство участия в командном соревновании.

## Новый план: оставшаяся работа в два уровня

## Запуск приложения

На хосте нужен Docker с Compose v2 и Linux-контейнерами. `app` отдаёт HTML/CSS/JS и API; `db` хранит данные; `mini-fsp-id` предоставляет мок; `mailpit` принимает локальную почту.

PowerShell, из корня проекта:

```powershell
if (!(Test-Path .env)) { Copy-Item .env.example .env }
docker compose up --build
```

Linux/macOS/Git Bash:

```bash
if [ ! -f .env ]; then cp .env.example .env; fi
docker compose up --build
```

Существующий `.env` не перезаписывать. По аудиту в проверенной папке его не было; это не описание файлов всех разработчиков. Настройки БД и JWT задаются через окружение. Для пароля в `DATABASE_URL` использовать URL-безопасные символы либо URL-кодирование.

| Сервис | Адрес |
| --- | --- |
| Главная | http://localhost:8000/ |
| Swagger app | http://localhost:8000/docs |
| OpenAPI app | http://localhost:8000/openapi.json |
| Liveness | http://localhost:8000/health |
| PostgreSQL readiness (`SELECT 1`, при отказе 503) | http://localhost:8000/readiness |
| Swagger мока | http://localhost:8001/docs |
| Mailpit | http://localhost:8025/ |
| SMTP внутри Compose | `mailpit:1025` |

Compose ждёт healthcheck БД; `app/start.py` дополнительно проверяет соединение, выполняет `alembic upgrade head` и запускает Uvicorn. Данные сохраняются в именованном volume. Dev override подключает исходники и reload; volume тестов добавлен в ходе разработки. Текущие volumes сверять с `compose.override.yaml`.

Для запуска без dev override:

```bash
docker compose -f compose.yaml up --build
```

**Ограничения текущего запуска:** миграции текущей версии не проверены аудитом на PostgreSQL; обновление заполненной БД требует исправления snapshot. Вопросы автоматически не загружаются. Не запускать обновление на ценных данных как замену проверке на отдельной БД.

`docker compose down` останавливает сервисы и сохраняет БД. Команду с `-v` для обычной остановки не использовать: она удаляет volumes.

## Мок ФСП и будущий Keycloak

Текущий локальный контракт:

- `GET /participants` — тестовые профили.
- `GET /participants/demo-1` — профиль участника.
- `GET /participants/demo-1/achievements` — персональные достижения.
- `demo-2` — пустая история; неизвестный ID — 404.

Данные читаются из `mock_fsp/data/*.json`. Соревнований, команд и подтверждения участия пока нет. Получение профиля по ID само по себе не подтверждает личность. `IdentityProvider` и `AchievementRegistry` — интерфейсы; HTTPX-клиенты используют `AsyncClient` с `base_url` и timeout. Сейчас они проверены через ASGI-мок, а не подключены к пользовательскому импорту.

Будущий OIDC-сценарий: перенаправление в Keycloak → callback с кодом → обмен кода через Authlib и проверки state/nonce/токена → внешняя личность `(issuer, sub)` → связь с `participant_id` → отдельный запрос достижений в реестр. Keycloak отвечает за вход, реестр — за участие и результаты. Для текущего MVP достаточно демо-привязки, согласованного контракта и документации этого перехода.

## Проверки и безопасные команды

### Проверки без записи в рабочую БД

Для локальных тестов нужны uv и Python 3.12. Тестовые зависимости не входят в runtime-образ. Команды из корня проекта:

```powershell
uv sync --locked --python 3.12
uv lock --check
uv run --locked pytest tests/backend -q
uv run --locked playwright install chromium
```

Для двух браузерных проверок главной и Swagger через временный Uvicorn:

```powershell
Remove-Item Env:APP_BASE_URL -ErrorAction SilentlyContinue
$env:RUN_E2E="1"
uv run --locked pytest tests/e2e/test_page.py -q
Remove-Item Env:RUN_E2E -ErrorAction SilentlyContinue
```

Эти проверки не требуют предметных записей в БД. Не распространять это утверждение на auth E2E или будущие тесты профилей/assessments.

Проверки Alembic без применения миграций, при наличии требуемых настроек:

```powershell
uv run --locked alembic heads
uv run --locked alembic history
uv run --locked alembic upgrade head --sql
```

Последняя команда только формирует SQL. Она не доказывает успешного применения миграций к новой или заполненной PostgreSQL.

### Integration и auth E2E

Не запускать весь `tests/integration/` или `tests/e2e/` с адресами рабочего приложения/БД. Нужны отдельные app, PostgreSQL, volume, мок/почта и явные настройки окружения; тесты должны создавать и очищать только собственные данные.

В текущем аудите безопасная тестовая конфигурация не подтверждена. Поэтому старая команда integration-прогона внутри обычного контейнера `app` убрана из инструкции. В задаче 1 нужно реализовать изоляцию и добавить сюда точные команды после проверки. Имя и параметры будущего тестового Compose-файла пока не утверждены.

На **подтверждённом отдельном тестовом окружении** проверить: `SELECT 1`, `current/heads/history`, применение миграций с нуля, обновление заполненной схемы, повторный `upgrade head`, ограничения, четыре сервиса и SMTP, restart, integration и auth E2E с очисткой. Простое изменение `DATABASE_URL` тестового процесса недостаточно, если браузер/API обращается к рабочему app.

## Письма подтверждения: Mailpit и внешний SMTP

Локально Docker Compose отправляет письма в Mailpit: интерфейс http://localhost:8025
(или порт `MAILPIT_PORT`). Mailpit не доставляет письма на внешние адреса.

Настройки: `SMTP_HOST`, `SMTP_PORT`, `SMTP_USERNAME`, `SMTP_PASSWORD`,
`SMTP_FROM_EMAIL`, `SMTP_FROM_NAME`, `SMTP_STARTTLS`, `SMTP_SSL`.
Для внешнего провайдера задайте его host/port, адрес отправителя и выданные им
credentials. STARTTLS обычно использует порт 587 (`SMTP_STARTTLS=true`),
implicit SSL — 465 (`SMTP_SSL=true`). Одновременно оба режима включать нельзя.
Логин и пароль задаются вместе; для Mailpit они пустые, TLS/SSL выключены.
Для Gmail используются SMTP/app-specific credentials Google в соответствии
с настройками аккаунта. Не сохраняйте реальные пароли в Git.

`APP_BASE_URL` — адрес приложения, доступный браузеру получателя письма:
локально `http://localhost:8000`, на сервере
`https://fspcareer.waytotarelka.ru`. Ссылка ведёт на существующий `/auth/verify`.
После изменения env пересоздайте app через `docker compose up -d`.

Проверка: регистрация → письмо → ссылка → подтверждённый email.
При ошибке SMTP аккаунт сохраняется, но приложение сообщает, что письмо не
отправлено. Войдите и откройте `/auth/check-email` для повторной отправки.
Успешная SMTP-отправка означает приём письма сервером, а не гарантию попадания
во входящие. Токены, срок действия и одноразовое подтверждение не изменены.
