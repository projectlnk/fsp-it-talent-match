# Минимальный шаблон

Python 3.12, FastAPI, SQLAlchemy, PostgreSQL, Alembic, Jinja2, локальные CSS/JS/HTMX. Backend и frontend работают в одном app; остальные сервисы: db, mini-fsp-id, mailpit. Предметные пакеты пока пусты.

## Карта репозитория

Цель проекта — подбор ИТ-специалистов с профилем, результатами тестирования и достижениями участника ФСП. Сейчас работает инфраструктурный шаблон; предметные сценарии ниже — план разработки.

Обозначения: `[работает]` — уже реализовано в шаблоне; `[заготовка]` — пустой пакет; `[план]` — предстоит добавить.

## Как проходят запросы

Ниже — схема будущих предметных запросов на базе существующего шаблона. Файлы `service.py`, `models.py` и модульные `router.py` пока не созданы.

- Браузер → `app/web/router.py` → `app/modules/<модуль>/service.py` → SQLAlchemy через `app/db/session.py` → PostgreSQL → результат возвращается в web-роутер → `app/templates/` → Jinja2/HTML → браузер.
- API-клиент → `app/main.py` → `app/api/router.py` → `app/modules/<модуль>/router.py` → `service.py` → SQLAlchemy → PostgreSQL → JSON-ответ.
- Основное приложение → сервис кандидата → адаптеры `app/integrations/fsp/identity.py` и `registry.py` → HTTP → `mock_fsp/main.py` в сервисе `mini-fsp-id` → синтетические данные `mock_fsp/data/`.
- `app/modules/*/models.py` → импорт моделей → `app/db/base.py: Base.metadata` → `migrations/env.py` → Alembic → новая ревизия в `migrations/versions/` → `upgrade head` → миграции PostgreSQL.

## Как разделить backend

Для каждого модуля создаём файлы по мере необходимости:

- `models.py` → SQLAlchemy-таблицы, связи и ограничения БД.
- `schemas.py` → Pydantic-схемы входных данных и ответов API.
- `service.py` → действия пользователя, правила, проверки доступа и границы транзакций. Этот код используют и JSON API, и HTML-страницы.
- `router.py` → HTTP-маршруты API, зависимости, вызов сервиса и преобразование ошибок в ответы.
- Простые запросы SQLAlchemy сначала остаются в `service.py`. Отдельный `queries.py` полезен в `matching` для составных фильтров и пагинации; отдельный `repository.py` — только если работа с БД действительно повторяется и мешает читать сервис.

Разделение ответственности:

- `app/modules/auth/` → пользователь, регистрация и вход, роли кандидата/работодателя, проверки доступа. Будущая внешняя личность хранится как `(issuer, sub)`; это отдельная сущность от идентификатора участника реестра ФСП.
- `app/modules/candidates/` → навыки, стек, желаемая роль и условия работы; связь с участником реестра, сохранённые достижения и формирование PDF. Результаты тестирования получает из `assessments`.
- `app/modules/employers/` → профиль работодателя, создание предложения с условиями и зарплатой, принятие/отклонение кандидатом. Предложения остаются здесь для первого MVP; новый модуль пока не нужен.
- `app/modules/assessments/` → тесты, попытки, ответы, результаты и категория кандидата. Правила категорий и содержание тестов нужно согласовать перед реализацией.
- `app/modules/matching/` → поиск кандидатов по категории и согласованным фильтрам, пагинация, доступ работодателя к профилям. Алгоритм подбора ещё не утверждён; сложные рекомендации и агрегатор вакансий за пределами первого MVP.
- `app/integrations/fsp/` → два независимых направления: подтверждение внешней личности и получение данных реестра. Существующее получение профиля через HTTPX само по себе не подтверждает личность. В будущем добавляем адаптер OIDC через Authlib; Keycloak отвечает за вход, отдельный API реестра — за достижения. Сейчас запуск Keycloak не требуется.

Общие точки подключения для двух разработчиков:

- API-роутер каждого модуля → один `include_router` в `app/api/router.py`; общий `app/main.py` обычно менять не нужно.
- HTML-маршруты → `app/web/router.py`. Когда страниц станет много, добавить `app/modules/<модуль>/web.py` и подключать его роутер здесь. Шаблоны раскладывать в `app/templates/<модуль>/`, чтобы не редактировать одну страницу всем вместе.
- Новые модели → запланированный `app/db/models.py`, который импортирует модели модулей; его импортировать в `migrations/env.py` до чтения `Base.metadata`. Сейчас такого файла нет: без загрузки моделей Alembic не увидит новые таблицы.
- Общие изменения в `app/api/router.py`, `app/web/router.py`, импортах моделей и `base.html` согласовывать отдельно. Основную работу вести в папке своего модуля, своих шаблонах и тестах.
- Миграции → согласовать порядок ревизий и проверять `alembic heads`. При параллельной работе избегать случайных независимых heads; сгенерированную миграцию всегда просматривать перед применением.

## Порядок разработки MVP

Это примерная разбивка задач. Правила категорий, вопросы тестов, точные фильтры и алгоритм подбора пока не утверждены.

1. **Основа и модели** → согласовать минимальные сущности пользователя, профилей, результатов, предложений и достижений; добавить связи и ограничения → `app/modules/*/models.py`, `app/db/`, `migrations/` → зависит от согласования полей и владельцев данных → готово, когда Alembic видит модели, миграции применяются на тестовой БД, повторный `upgrade head` безопасен, связи и ограничения проверены в `tests/integration/`. Создавать таблицы небольшими ревизиями по мере следующих этапов.

2. **Регистрация и права доступа** → регистрация, вход/выход, роли, защита чужих данных → `app/modules/auth/`, `app/api/router.py`, `app/web/router.py`, `app/templates/auth/`, `migrations/` → зависит от модели пользователя и согласованного способа входа → готово, когда pytest в `tests/backend/` проверяет разрешённые и запрещённые действия, а Playwright в `tests/e2e/` проходит регистрацию и вход. Реальный ФСП ID для локального входа не нужен.

3. **Профили** → кандидат редактирует навыки, стек, роль и условия; работодатель заполняет свой профиль → `app/modules/candidates/`, `app/modules/employers/`, `app/templates/candidates/`, `app/templates/employers/`, `migrations/` → зависит от регистрации и прав → готово, когда данные сохраняются после перезагрузки страницы, чужой профиль нельзя редактировать; pytest проверяет валидацию/API и сохранение в БД, Playwright — заполнение форм.

4. **Тестирование и категории** → согласовать вопросы и правила, реализовать прохождение теста и сохранение результата/категории → `app/modules/assessments/`, `app/templates/assessments/`, `migrations/` → зависит от пользователя, профиля и утверждённых правил → готово, когда pytest проверяет расчёт на согласованных примерах, integration — сохранение попыток, Playwright — прохождение и отображение результата. Не выдавать временную формулу оценки за утверждённую.

5. **Поиск кандидатов** → поиск работодателем по категории и согласованным фильтрам, просмотр профиля, пагинация → `app/modules/matching/`, `app/templates/matching/`, чтение данных `candidates` и `assessments` → зависит от профилей, категорий и прав → готово, когда pytest/integration проверяют фильтры, пустую выдачу и доступ, Playwright — поиск и открытие профиля. Для MVP достаточно согласованного поиска без сложного рекомендательного алгоритма.

6. **Предложения и ответы** → работодатель отправляет условия и зарплату; кандидат принимает или отклоняет → `app/modules/employers/`, `app/templates/employers/`, `app/templates/candidates/`, `migrations/` → зависит от профилей и выбора кандидата → готово, когда предложение доступно только участникам, повторный ответ не портит состояние; pytest проверяет переходы и права, integration — сохранение, Playwright — отправку и ответ. Если включаем email-уведомления, проверять доставку через Mailpit.

7. **Привязка ФСП и импорт достижений** → отдельно реализовать тестовую привязку личности/участника и импорт; хранить ID реестра отдельно от `(issuer, sub)` → `app/modules/auth/`, `app/modules/candidates/`, `app/integrations/fsp/`, `mock_fsp/`, `app/templates/candidates/`, `migrations/` → зависит от профиля, контракта мока и данных об участии → готово, когда повторный импорт не создаёт дубли, чужое командное достижение не попадает в профиль, сбои реестра обрабатываются, в UI есть отметка «Демонстрационные достижения». pytest проверяет правила и адаптеры, integration — реальный HTTP к моку и уникальность в БД, Playwright — привязку и импорт.

8. **PDF-резюме** → согласовать состав резюме и способ генерации, сформировать PDF из профиля → `app/modules/candidates/` (при необходимости `resume.py`), `app/templates/candidates/`, `app/api/router.py` или web-роутер → зависит от профиля; для полного резюме — от результатов и импорта → готово, когда пользователь скачивает свой корректный PDF, демонстрационные достижения явно помечены, чужое резюме недоступно. pytest проверяет содержимое и права, Playwright — скачивание. Выбор библиотеки PDF — отдельная будущая задача.

9. **Сквозная проверка** → кандидат регистрируется, заполняет профиль, проходит тест, импортирует демо-достижения; работодатель находит его и отправляет предложение; кандидат отвечает и скачивает PDF → `tests/backend/`, `tests/integration/`, `tests/e2e/` → зависит от предыдущих этапов → готово, когда сценарий проходит на запущенном Compose, миграции и restart работают, нет ошибок браузера и утечек доступа. Проверить и отказ предложения, и пустой поиск, и недоступность мока.

Общий порядок: **модели → регистрация/права → профили → тестирование/категории → поиск → предложения → ФСП/импорт → PDF → сквозной прогон**.

Независимые работы можно вести параллельно:

- **Подготовка mini-fsp-id** → согласовать собственный контракт API; добавить синтетические соревнования, команды, участие и достижения → `mock_fsp/schemas.py`, `mock_fsp/main.py`, `mock_fsp/data/`, `tests/backend/` → можно начать с первого этапа, без готовой регистрации → готово, когда контракт описан в `/docs` и README, данные согласованы, API проверяет связи и возвращает ожидаемые ошибки. Это демонстрационный реестр, не официальный API ФСП.
- **Проверка командных достижений** → привязать достижение к соревнованию и команде, а человека — к участию в этом соревновании → сначала контракт и фикстуры в `mock_fsp/`, затем импорт в `app/modules/candidates/` → готово, когда участие в другой команде или другом соревновании не даёт чужого достижения. Ключи для защиты от дублей согласовать с контрактом и закрепить ограничениями БД.
- **Два разработчика после этапа регистрации** → один делает `candidates` и `assessments`, другой — `employers` и подготовку `mock_fsp`; поиск подключается после появления профилей и категорий → общие схемы и точки подключения согласовать заранее. Импорт ФСП можно разрабатывать параллельно поиску и предложениям, как только готовы профиль и мок.

Для любой небольшой задачи: **схемы/модели → миграция при изменении БД → сервис → API и/или HTML-маршрут → шаблон → подходящий тест**. Команды запуска и проверок приведены ниже. Использовать отдельную тестовую БД для тестов, которые создают или меняют предметные данные.

## Запуск

На хосте нужен только Docker с Compose v2 и поддержкой Linux-контейнеров. Из этой папки:

```powershell
if (!(Test-Path .env)) { Copy-Item .env.example .env }
docker compose up --build
```

Linux/macOS: `cp .env.example .env`. Не перезаписывайте уже настроенный .env. Пример содержит только локальные тестовые параметры. Для пароля в DATABASE_URL используйте URL-безопасные символы либо задайте DATABASE_URL с URL-кодированным паролем в Compose.

- Страница: http://localhost:8000/
- Swagger приложения: http://localhost:8000/docs
- Liveness: http://localhost:8000/health
- PostgreSQL readiness (SELECT 1, при отказе 503): http://localhost:8000/readiness
- Swagger мока: http://localhost:8001/docs
- Почта Mailpit: http://localhost:8025/; SMTP внутри сети: mailpit:1025.

Compose ждёт healthcheck БД; app дополнительно проверяет соединение, выполняет `alembic upgrade head` и только затем запускает Uvicorn. Начальная миграция создаёт историю alembic_version без предметных таблиц. Данные PostgreSQL сохраняются в именованном volume. Исходники app/migrations/mock_fsp подключены volumes; reload включён автоматически через compose.override.yaml. Зависимости в контейнере находятся в /opt/venv. Для запуска без dev override: `docker compose -f compose.yaml up --build`.

`docker compose down` останавливает сервисы и сохраняет БД. `docker compose down -v` удаляет данные БД.

## Мок и интеграции

GET /participants — тестовые профили; GET /participants/demo-1 — профиль; GET /participants/demo-1/achievements — достижения. demo-2 имеет пустой список достижений, неизвестный id возвращает 404. Данные читаются из mock_fsp/data/*.json. Это локальный контракт, не официальный API ФСП ID.

IdentityProvider и AchievementRegistry — интерфейсы; HTTPX-клиенты принимают AsyncClient с base_url и timeout. Обработку авторизации реального провайдера следует добавить позже.

Будущий вход: Keycloak как OIDC-провайдер, Authlib для authorization code flow, discovery, проверки state/nonce и токенов; конфигурация issuer/client_id/client_secret через окружение, пользовательские сессии и права в модуле auth. Keycloak, Authlib и полноценная авторизация сейчас не подключены.

## Проверки

Тестовые зависимости не входят в runtime-образ. Для тестов на хосте нужны uv и Python (uv может загрузить Python):

```powershell
uv sync --locked --python 3.12
uv run --locked pytest tests/backend -q
uv run --locked playwright install chromium
$env:RUN_E2E="1"
uv run pytest tests/e2e -q
```

Проверки реальной БД и миграции через сеть Compose без установки Python на хост:

```powershell
docker compose exec app uv run --locked --group dev python -c "from sqlalchemy import text; from app.db.session import engine; c=engine.connect(); print(c.execute(text('SELECT 1')).scalar_one()); print(c.execute(text('SELECT version_num FROM alembic_version')).scalar_one()); c.close()"
docker compose exec app alembic current
```

Полный integration-прогон внутри app:

```powershell
docker compose exec -e RUN_INTEGRATION=1 -e APP_BASE_URL=http://localhost:8000 -e FSP_BASE_URL=http://mini-fsp-id:8000 app uv run --locked --group dev pytest tests/integration -q
```

Для integration-тестов на хосте БД должна быть доступна по DATABASE_URL; Compose по умолчанию не публикует её порт. Можно выполнять тесты внутри app, указав APP_BASE_URL/FSP_BASE_URL для сервисных проверок (см. tests/integration).

.env, секреты, окружения, кэш, логи и результаты тестов исключены из Git и Docker build context. uv.lock включён в проект; после изменения зависимостей выполните uv lock и пересоберите образ. Git remote, коммиты и push не настроены.

HTMX 2.0.11 хранится локально; источник: https://htmx.org/docs/ и https://cdn.jsdelivr.net/npm/htmx.org@2.0.11/dist/htmx.min.js (Zero-Clause BSD).
Справка по установке зависимостей в образ: https://docs.astral.sh/uv/guides/integration/docker/.

## Локальная разработка в этом окружении

Браузерный тест самостоятельно запускает временный Uvicorn на свободном порту и останавливает его после проверки.
БД для него не нужна. Для проверки внешнего сервера задайте APP_BASE_URL.

Проверка lock-файла: uv lock --check. Генерация SQL без БД: uv run --locked alembic upgrade head --sql.

## Проверки Docker после перезагрузки

Проверено 2026-10-07: Docker Engine и Compose доступны, конфигурация корректна,
`docker compose up --build -d` успешно собирает и запускает все четыре сервиса.
Существующий `.env` сохранён. `app`, `db` и `mailpit` healthy; мок отвечает на HTTP-запросы.
После запуска Docker Desktop повторить проверки можно так:

```powershell
docker compose up --build -d --wait
uv run --locked pytest tests/backend -q
docker compose exec app alembic current
docker compose exec -e RUN_INTEGRATION=1 -e APP_BASE_URL=http://localhost:8000 -e FSP_BASE_URL=http://mini-fsp-id:8000 app uv run --locked --group dev pytest tests/integration -q
$env:RUN_E2E="1"
$env:APP_BASE_URL="http://localhost:8000"
uv run --locked pytest tests/e2e -q
```

Integration-тесты проверяют SELECT 1, соответствие миграций heads Alembic, оба Swagger/OpenAPI, readiness, API мока и Mailpit.
Тестовые зависимости не входят в runtime-образ; uv run в контейнере устанавливает их только для проверки.
.env в этом окружении уже подготовлен, копировать поверх него не нужно.
Лицензия HTMX находится в app/static/vendor/HTMX-LICENSE.txt.
